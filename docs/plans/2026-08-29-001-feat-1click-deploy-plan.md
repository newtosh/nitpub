# 1-Click Deploy - Plan

## Goal Capsule

**Objective:** Cut the friction of standing up a nitpub instance for the existing target persona (self-hosting indie blogger, technically capable of running a Go binary on a VPS) by replacing manual SSH setup with a copy-paste startup-script flow on three VPS providers, with affiliate revenue attached where each provider offers a program.

**Product authority:** [[nitpub-product-scope]] (v1 scope), `STRATEGY.md` (target persona: self-hosting indie blogger, VPS-comfortable). This plan extends deploy UX; it does not change persona or product shape.

**Open blockers:** none.

## Product Contract

**Product Contract preservation:** changed — KD4 (see below). Mechanism-level correction from Phase 1 research, not a scope or outcome change: same objective, better implementation path. No other Key Decision touched.

### Key Decisions

1. **Same technical persona, less friction** *(session-settled 2026-08-29)* — no first-boot setup wizard. Domain/actor are supplied via script variables (DO/Vultr) or UDF fields (Linode) at creation time rather than edited into `config.toml` post-deploy; DNS pointing and any further `config.toml` customization remain manual, same as today.
2. **v1 ships the self-serve script, not marketplace listings** *(session-settled 2026-08-29)* — provider marketplace review (DigitalOcean, Vultr, Linode/Akamai) is external and can take days-to-weeks, which would put the EOM-August ship date hostage to three review queues outside our control. v1 delivers a docs page with affiliate-tagged links plus a copy-paste startup script; formal marketplace 1-click app submissions are a fast-follow.
3. **Three providers: DigitalOcean, Vultr, Linode/Akamai** *(session-settled 2026-08-29)* — all three run real commission-based affiliate/referral programs (confirmed via research: DO 10% recurring via CJ Affiliate, Vultr ~$30-100 CPA, Linode/Akamai 5% per sale) and accept a startup script at instance creation. Hetzner dropped (referral credit only, no commission program). Vercel dropped (serverless — mismatched to nitpub's persistent SQLite + long-running ActivityPub federation state).
4. **Deploy mechanism** *(changed 2026-08-29 — see below)* — ~~one shared cloud-init script adapted from `deploy/bootstrap-dev-vps.sh`~~ → **a thin wrapper around the existing `scripts/install.sh` → `nitpub install` flow**, one shared plain-bash variant for DigitalOcean + Vultr, and a Linode StackScript (UDF-format) variant. Repo is public, confirmed via `gh repo view`, so no auth step is needed to fetch the installer.
   - **Why changed:** Phase 1 research found `scripts/install.sh` already exists, downloads a release binary, and hands off to `nitpub install --yes --domain=... --actor=... --with-caddy --with-federation` (see `docsite/docs/guide/install.md`). This needs no Go/Node/git-clone on the VPS and is already the documented, maintained install path — strictly simpler and lower-risk than adapting the source-build bootstrap script the brainstorm assumed.
   - **Also corrected:** affiliate links from each provider's program are plain referral/signup links, not deep-linked forms with prefilled instance options — no provider supports prefilling droplet/instance creation via URL params. Docs must not imply a literal one-click "everything filled in" experience; the click is to sign up/log in via the affiliate link, then the user pastes the script during normal instance creation.
   - **Upside found:** Linode/Akamai StackScripts support UDF (User Defined Fields) — domain/actor/password become real named form fields on Linode's create-instance page, and a published StackScript gets a shareable deploy link. This is closer to genuine 1-click than DO/Vultr's paste-in-a-text-box flow, with no marketplace review required.

### Requirements

  - An affiliate/referral-tagged link to that provider's signup or dashboard.

## Planning Contract

### Key Technical Decisions

**KTD1 — Wrap `scripts/install.sh`, don't reimplement it.** *(Governs Key Decision 4)* The provider scripts only set env vars and call the existing installer; they must not duplicate its download/checksum/install logic. Keeps a single maintained install path — if `install.sh` changes, provider scripts don't need updates.

**KTD2 — Auto-generate the admin password, write it to a root-only file, don't prompt for it.** `deploy/bootstrap-dev-vps.sh` precedent is narrower than it first looks: it generates the config `secret` (`openssl rand -hex 32`) and writes it into `config.toml` for the operator to retrieve later with `grep '^secret' $CONFIG_FILE` — it does **not** echo it to the boot log, and it has no admin-password step at all (that's a separate interactive flow today). Echoing a generated admin password directly to console/boot-log output is new territory this plan introduces, and most providers retain that output in the dashboard/API for the life of the instance — recoverable by anyone with later read access to the account, not just at creation time. Write the generated password to a root-only file on the instance (e.g. `/root/nitpub-admin-password`, mode 600) instead, and have the docs page instruct retrieval via SSH. Keeps the paste-in script to exactly two required edits (domain, actor), consistent with Key Decision 1 (no wizard, minimal friction beyond what a technical user already tolerates).

**KTD3 — Two script artifacts, not three.** DO and Vultr both accept a plain bash script pasted into a text field with no special header requirements for non-cloud-config scripts (confirmed: DO via control panel/API/doctl `--user-data`; Vultr via "Startup Scripts"). One script file serves both. Linode's StackScript format is a different file (UDF header block) by platform requirement, not by choice — not a 4th variant, a genuinely separate mechanism.

### Risks & Dependencies

- **Curl-pipe install at unattended root boot has no local review step.** The startup scripts fetch and execute `scripts/install.sh` from a mutable GitHub ref as root with no chance for the user to inspect it first, unlike today's manual flow. Primary mitigation (HTTPS, public/reviewable repo) already applies; pinning `scripts/install.sh` to a release tag or commit SHA rather than a branch reference would tighten this further — deferred, not blocking.
- **Generated secrets pass as CLI args, briefly visible via `/proc/<pid>/cmdline` to other local processes.** Flagged by `ce-code-review`'s security pass: `--secret`/`--password` travel as literal argv to `nitpub install` for the few seconds it runs. Low practical risk on a single-tenant fresh VPS. A fix (env-var flags instead of argv, if `cmd/nitpub/install_cmd.go` supports it) is out of this plan's scope — deferred, not applied.
- **Published Linode StackScript is public and clonable.** A third party could republish a similarly-named StackScript to phish users searching for a nitpub deploy script. No mitigation planned for v1 beyond linking the canonical StackScript from the docsite page and `install.md`.

### Sources & Research

- `deploy/bootstrap-dev-vps.sh`, `deploy/nitpub.service`, `deploy/config.toml.example` — prior manual path, superseded as the basis for this plan by the above.

## Implementation Units

### U1. Shared DigitalOcean + Vultr startup script

**Goal:** One pasteable bash script that installs nitpub unattended via the existing installer.

**Requirements:** Advances Requirements (script), Key Decision 4, KTD1, KTD2, KTD3.

**Dependencies:** none.

**Files:**
- `deploy/startup-do-vultr.sh` (new)

**Approach:**
- Top-of-file editable block: `NITPUB_DOMAIN`, `NITPUB_ACTOR` (only two required edits).
- Generate the admin password inline (`openssl rand -hex 16` or equivalent). Write it to a root-only file (e.g. `/root/nitpub-admin-password`, mode 600) rather than echoing it to console/boot-log output, which most providers retain in the dashboard/API beyond instance creation (see KTD2). Also print the `/login` URL to the script's own output.
- Invoke `scripts/install.sh` (via `curl -fsSL .../scripts/install.sh | bash -s -- ...`) forwarding `--yes --domain "$NITPUB_DOMAIN" --actor "$NITPUB_ACTOR" --secret "$(openssl rand -hex 32)" --password "$GENERATED_PASSWORD" --with-caddy --with-federation --no-analytics` — flags verified against `cmd/nitpub/install_cmd.go` (all accepted; `--yes` requires `--password`).
- Runs as root (both DO user-data and Vultr startup scripts execute as root on first boot) — no `sudo` needed, matching `scripts/install.sh`'s own root check.

**Patterns to follow:** `deploy/bootstrap-dev-vps.sh`'s config-`secret`-generation convention (generate, write to config, operator retrieves later — not echoed to boot log); `scripts/install.sh`'s existing arg-forwarding contract (documented in its header comment).

**Test scenarios:**
- Happy path: paste script into a fresh DigitalOcean Droplet's User Data field with valid domain/actor, instance boots, `nitpub install` completes, `/healthz` returns 200, webfinger resolves for the configured actor.
- Happy path: same on a fresh Vultr instance's Startup Script.
- Edge case: domain not yet pointed at the instance's IP at boot time — `nitpub install --with-caddy` should not hang or fail destructively (verify against `install.md`'s documented `--with-caddy` behavior; if it requires DNS to already resolve, note that as a doc caveat rather than a script bug).
- Error path: script re-run on an already-installed instance — should be a no-op or safe report, per `install.md`'s "Re-running `nitpub install` is lossless" guarantee, not a corrupting double-install.

**Verification:** Manually create one real DigitalOcean Droplet (cheapest tier) using the script, confirm `/login`, `/healthz`, and webfinger all work per `install.md`'s existing "Verify" steps. Vultr can be verified the same way or reasoned about from the shared script content plus Vultr's documented Startup Script execution model if a second real instance isn't practical to spin up during this pass.

### U2. Linode/Akamai StackScript variant

**Goal:** A StackScript with `domain`/`actor` as UDF fields, giving Linode's create-instance page real form inputs instead of a pasted script.

**Requirements:** Advances Requirements (script), Key Decision 4 upside, KTD1, KTD2, KTD3.

**Dependencies:** none (parallel to U1; shares the same underlying install invocation, different wrapper format).

**Files:**
- `deploy/startup-linode.stackscript.sh` (new)

**Approach:**
1. UDF header block declaring `domain` and `actor` fields (per Akamai's documented StackScript UDF syntax), no default for `domain`, a sensible default for `actor` matching `config.toml.example`'s `actor = "user"`.
2. Body reads `$DOMAIN` / `$ACTOR` (StackScript's UDF substitution convention) and calls the same `scripts/install.sh` invocation as U1, generating the password and writing it to the same root-only file the same way (KTD2).
3. Publish the StackScript on the account (public, per Akamai's docs) to get the shareable "Deploy" link referenced from the docsite page — this is what gets Linode closer to genuine one-click.

**Patterns to follow:** Akamai's StackScript UDF syntax from `getting-started-with-stackscripts`; same install-invocation pattern as U1.

**Test scenarios:**
- Happy path: use the published StackScript's deploy link, fill in domain/actor in the real UDF form fields, confirm the resulting Linode reaches `/healthz` and webfinger, same as U1's DO/Vultr checks.
- Edge case: `actor` left at its UDF default — confirm the resulting `acct:user@domain` webfinger resolves correctly, matching `config.toml.example`'s documented default.

**Verification:** Publish the StackScript, walk the deploy link end to end on one real Linode instance, confirm parity with U1's verification outcomes.
